# The component manifest

[`component-manifest.json`](../../component-manifest.json) is the published, machine-readable
description of the component surface. It ships in the package as
**`@qeetrix/ui/manifest.json`**, so docs sites, MCP tooling and code generators can discover
what exists — and what it promises — without parsing barrels or source.

It is **generated**. Never hand-edit it. Regenerate with:

```bash
bun run build:manifest
```

---

## Where the data comes from

Three inputs, and nothing else:

| Input | Provides |
|:--|:--|
| the filesystem + [`scripts/config/category-map.json`](../../scripts/config/category-map.json) | `slug`, `name`, `category`, `layer`, the import paths |
| the component source | `capabilities`, `states`, `api`, `testing` |
| [`src/manifests/component-registry.ts`](../../src/manifests/component-registry.ts) | `status`, `accessibility`, `deprecation`, reviewed capability overrides |

Anything neither derivable nor declared is emitted as `"unknown"` or `null`.

> **A missing fact and a negative fact are different things.** The generator never writes
> `false` for something it merely failed to find. `"unknown"` is a review backlog item;
> `"unsupported"` is a decision; `"not-applicable"` is a statement that the question does not
> arise.

## Document shape

```json
{
  "$schema": "https://qeetrix.qeet.in/manifest.schema.json",
  "schemaVersion": 2,
  "name": "@qeetrix/ui",
  "version": "1.0.3",
  "description": "…",
  "generated": "2026-08-22",
  "styles": "@qeetrix/ui/styles.css",
  "tokens": "@qeetrix/ui/tokens.json",
  "count": 145,
  "categories": { "actions": 7, "…": 0 },
  "statuses": { "experimental": 0, "beta": 0, "stable": 144, "deprecated": 1 },
  "components": [ … ]
}
```

`count`, `categories` and `statuses` are tallies, and `bun run check:contract` fails if any of
them disagrees with `components` — a stale manifest is a detectable manifest.

## Entry shape

```json
{
  "slug": "button",
  "name": "Button",
  "category": "actions",
  "layer": "components",

  "import": "@qeetrix/ui",
  "deepImport": "@qeetrix/ui/components/button",
  "groupImport": "@qeetrix/ui/components/actions",

  "status": "stable",
  "capabilities": {
    "rtl": "supported",
    "darkMode": "supported",
    "density": "supported",
    "ssr": "server-safe",
    "reducedMotion": "unknown"
  },
  "states": ["hover", "focus-visible", "active", "disabled", "invalid", "expanded"],
  "api": {
    "variants": ["default", "outline", "secondary", "ghost", "destructive", "link"],
    "sizes": ["default", "xs", "sm", "lg", "icon", "icon-xs", "icon-sm", "icon-lg"],
    "variantGroups": ["size", "variant"]
  },
  "accessibility": { "required": true, "pattern": "button" },
  "testing": {
    "unit": true, "accessibility": true, "interaction": true, "visual": true, "hydration": false
  },
  "deprecation": null,

  "story": true,
  "tested": true,
  "deprecated": false
}
```

### Identity

| Field | Notes |
|:--|:--|
| `slug` | kebab-case module name. Unique across the library. |
| `name` | PascalCase form of the slug. Validated, not stored twice. |
| `category` | One of the ten families. Must agree with `category-map.json`. |
| `layer` | The architecture layer — `components` today. See [component-layers.md](../architecture/component-layers.md). |

`name` is the PascalCase of `slug`, which is the *module* name — it is not always an exported
symbol name (`json-tree` exports `JSONTree`; `chart` exports `ChartContainer` and friends).
Resolve exports through the package's types, not by transforming the slug.

### Import surface

`import` is the specifier that exports the component: `@qeetrix/ui` normally, or the deep path
when the module is `@barrel-exclude`. `deepImport` is stable regardless of the component's
category — the flat façade is generated by
[`scripts/build/subpath-shims.mjs`](../../scripts/build/subpath-shims.mjs), so a category move
never reaches a consumer.

### `status`

`experimental` · `beta` · `stable` · `deprecated`. Declared, never derived — maturity is a
decision. See [component-status.md](../governance/component-status.md).

### `capabilities`

Four fields take `supported` · `unsupported` · `not-applicable` · `unknown`; `ssr` takes
`server-safe` · `client-boundary` · `unknown`.

Derived from the source by
[`scripts/lib/component-source.mjs`](../../scripts/lib/component-source.mjs), where the
detection rules are data rather than control flow:

| Capability | `supported` when | `unknown` when | `not-applicable` when |
|:--|:--|:--|:--|
| `rtl` | uses logical utilities (`ps-`, `pe-`, `ms-`, `me-`, `start-`, `end-`, `text-start`, `rtl:`) | uses physical utilities only | no directional styling at all |
| `darkMode` | paints anything | — | paints nothing |
| `density` | reads `--qx-density-*`, `useDensity` or `data-qx-density` | has metrics density could drive, but does not read it | no metrics to scale |
| `reducedMotion` | uses `usePrefersReducedMotion`, `motion-reduce:` or `prefers-reduced-motion` | something moves and nothing handles it | nothing moves |
| `ssr` | `server-safe` — no `"use client"` | — | `client-boundary` — declares `"use client"` |

Two of those need justifying.

**`darkMode` from "paints anything".** Colour in a Qeetrix component can only come from a
semantic token: `bun run check:token-usage` rejects raw values in component source, and
`bun run check:contrast` holds every semantic text/surface pair to WCAG AA in *both* themes. So
using colour at all *is* the evidence — the token discipline supplies the rest. A component that
paints nothing has no theme surface to support.

**Physical utilities give `unknown`, not `unsupported`.** `left-1/2 -translate-x-1/2` centres a
dialog identically in both directions. Presence of a physical property is a reason to look, not
a defect — so it lands in the review backlog rather than being reported as a failure.

`capabilities` can be overridden per component in the registry, for cases where a review has
settled what the signal could not. No overrides are declared today.

### `states`

The interaction states the component demonstrably handles, from
[`INTERACTION_STATES`](../../src/contracts/states.ts). Detection is conservative — only
unambiguous markers count (`hover:`, `aria-invalid`, `data-checked`, …) — so an **empty list
means "nothing detected", never "nothing supported"**.

States that exist in behaviour but leave no styling fingerprint are declared in the registry.
The overlay components are the example: they take Base UI's `Root.Props`, so their open/closed
state lives in the props contract where no CSS marker appears.

### `api`

Read statically from the component's `cva()` calls. `variants` is the `variant` group, `sizes`
is the `size` group, `variantGroups` lists every group found (including boolean modifiers like
`selected` or `fullWidth`, which are a legitimate `cva` idiom).

All three are `null` for a component that does not use `cva` — "not recorded", which is not the
same as an empty variant surface. 21 of 145 components record a variant surface today.

### `accessibility`

```ts
{ required: boolean; pattern: AriaPattern | null }
```

`pattern` is three-valued:

- an **APG pattern name** (`"dialog"`, `"combobox"`, `"treeview"`, …) — the component implements
  it, and breaking it is a breaking change
- **`"none"`** — reviewed, and no APG pattern applies
- **`null`** — not reviewed yet

Two consistency rules are enforced: `required: true` requires a pattern, and a real APG pattern
requires `required: true`. `"none"` may sit either side — `required: true, pattern: "none"` is a
native-semantics contract (an `<input>` must be labelled), `required: false, pattern: "none"` is
"reviewed and presentational".

Seeded patterns are evidenced by the component's Base UI primitive or its explicit ARIA role.
59 of 145 components are reviewed; the rest are `null`, which is the backlog rather than a
claim. `bun run check:contract --verbose` lists them.

### `testing`

Every field is observed, not declared:

| Field | True when |
|:--|:--|
| `unit` | a colocated `__tests__/<slug>.test.tsx` exists |
| `accessibility` | that suite runs `axe`, or the component is in `src/__tests__/a11y.test.tsx` |
| `interaction` | that suite drives the component with `user-event` or `fireEvent` |
| `visual` | a story exists in the sibling `qeetrix-story` workshop |
| `hydration` | the component is exercised by `src/__tests__/hydration.test.tsx` |

`visual` reads the sibling repository if it is checked out, and is simply `false` when it is
not — the manifest build never writes outside this package.

### `deprecation`

`null`, or a record with `since`, `reason`, `replacement`, `migration`, `removeIn`. Required
when `status` is `"deprecated"`, forbidden otherwise. See
[deprecations.md](../governance/deprecations.md).

## Compatibility

`schemaVersion: 2` added the governance fields. **Every version-1 field is still emitted, with
identical values** — `slug`, `name`, `category`, `import`, `deepImport`, `groupImport`, `story`,
`tested`, `deprecated`. A version-1 consumer needs no changes.

The three booleans are now mirrors: `story` = `testing.visual`, `tested` = `testing.unit`,
`deprecated` = `status === "deprecated"`. The contract check fails if a mirror ever drifts, so
they cannot quietly diverge. New consumers should read the structured fields.

Adding a field is a **minor**. Removing one, or changing what one means, is a **major** and a
`schemaVersion` bump.

## Validation

```bash
bun run check:contract              # validate
bun run check:contract --verbose    # also print the review backlog
```

The gate is implemented as a pure function
([`scripts/lib/contract.mjs`](../../scripts/lib/contract.mjs)) over plain data, so the negative
cases are unit-tested in `src/__tests__/component-contract.test.ts` rather than only being
exercised when something is already broken. Diagnostics name the component, the issue, the
expectation and the file:

```text
Component Contract Error

Component: Dialog

Issue:
  Missing accessibility.pattern

Expected:
  an APG pattern name, or "none" when no pattern applies

Why:
  a component with required: true has an accessibility contract to name

Location:
  src/manifests/component-registry.ts
```
